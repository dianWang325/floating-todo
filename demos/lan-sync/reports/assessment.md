# 同步 demo 实测与架构结论

实验日期：2026-10-21（Asia/Shanghai）。宿主机 `192.168.11.10`，三个非特权 Debian LXC，
第一轮另有一个隔离 Headscale 控制容器。后续三节点迁入现有 Headscale 并完成验证，
隔离控制容器已停止；正式桌面应用未改动。

**结论：现有版本模型可以支撑局域网和 Tailscale 的双向同步。**
已验证发现、双短码配对、版本中继、冲突保留与替换、断线补齐和崩溃恢复。
适合继续做正式架构集成；本实验不是生产安全认证或长期可靠性证明。

## 现有 Headscale 网络补充验证

节点地址为 100.64.0.5、100.64.0.6、100.64.0.9。管理端授权后最初因访问策略限制，
节点彼此不可见；放行三者之间的 TCP 47831 后，原配对自动认证新地址，迁移前 1553 个版本完整保留。
此后重新验证了临时码与固定码配对、三节点同步、并发冲突保留与替换，以及 VPN 停止/重启补齐。

现有网络暴露了发现调度缺陷：一次发起全部候选探测，超过服务端四并发限制的候选被跳过。
已改为四并发分批等待，失败探测不阻止后续批次；新增 11 候选回归用例。
Mac 与 Linux 的全部 11 项 demo 测试通过，三 LXC 实测发现完整。

30 次修改的同步延迟中位数 415.31 ms、P95 549.05 ms、最大 565.62 ms；
短码配对 45.40–104.09 ms，VPN 重启后 18.351 秒自动收敛。
45 秒采样中，应用 RSS 为 76.12–102.29 MiB，应用 CPU 为单核的 0.186–0.216%，
应用层流量约 180–193 B/s；VPN cgroup 内存 34.34–41.44 MiB、CPU 0.325–0.370%。
RSS 与 cgroup 内存是不同口径，不直接相加。采样期同宿主机运行过一次 Linux 回归测试，
这些数值是现场观测，不能视作严格隔离的性能基准。

现有历史量、网络设备及控制平面均与第一轮不同，延迟差异不能单独归因于 Headscale。
本轮仍是同宿主机测试，不代表跨地域网络表现。原始数据见 `existing-headscale-results.json`。
最终三节点各有 1588 个版本，摘要一致且同步错误为空，证据见 `existing-headscale-final.json`。

## 第一轮延迟与资源

每节点限制 256 MiB、0.5 核，应用服务进一步限制 160 MiB、40% 单核。
延迟从控制端发起一次修改，到三个独立节点的完整版本集合摘要相同为止，
包含控制请求、120 ms 调度、传输、SQLite 保存和观测轮询，不是纯网络 RTT。
每种网络 30 个样本，P95 使用 nearest-rank。

| 项目 | LAN | Tailscale |
| --- | ---: | ---: |
| 自动同步中位延迟 | 250.55 ms | 263.18 ms |
| 自动同步 P95 | 283.25 ms | 288.52 ms |
| 最大观测延迟 | 346.52 ms | 360.04 ms |
| 短码配对 | 39.96–51.84 ms | 36.31–45.15 ms |
| 应用空闲 CPU，占单核 | 0.182%–0.259% | 0.174%–0.188% |
| 应用消息负载，双向合计 | 约 172–175 B/s | 约 167 B/s |
| 空闲应用 RSS | 75.36–89.86 MiB | 78.60–83.42 MiB |
| Tailscale 服务 cgroup 内存 | — | 35.35–40.09 MiB |
| Tailscale 空闲 CPU，占单核 | — | 0.180%–0.196% |

应用消息负载不含 HTTP/TCP/IP、mDNS 和 VPN 包头，不能当成网卡流量。
RSS 与 cgroup 计费内存不是同一指标，不应直接相加计算实际总内存。
最终负载后网卡和 cgroup 采样另外保存于 `resource-results.json`。
LAN 最终延迟样本采集时 VPN 守护进程已启动，但应用通信使用 LAN 地址。

初始 LAN 测试中，300 次逐条修改在 3,777 ms 内提交并收敛；随后 180 秒持续修改，
三个节点最终均为 401 个版本，最大采样应用 RSS 为 100.53 MiB。
最终 LAN 验证后，三个节点均为 431 个版本。

后续在真实 Tailscale 路径上新增 1,000 次逐条修改，提交并收敛共 43,258 ms，
三节点均到达 1,466 个版本。这个数包含逐条业务建模、索引计算、同步和 SQLite 事务，
不是“传输 1,000 个已有版本”的耗时。它说明当前全量实体扫描与索引重算会随历史增长增加成本。
正式集成应引入按实体和分桶的增量索引，保留批量事务接口；不应把无限历史都放入高频全量扫描。
随后五分钟又产生 87 次修改，最终三个节点均为 **1,553 个版本**，
没有非预期服务重启，期间三个应用 RSS 最大采样值分别为 89.39、91.86、98.89 MiB。

负载结束后约 35.5 秒的独立空闲采样显示：

| 项目 | 971 | 972 | 973 |
| --- | ---: | ---: | ---: |
| 应用服务 cgroup 内存 | 91.59 MiB | 77.28 MiB | 100.91 MiB |
| VPN 服务 cgroup 内存 | 29.22 MiB | 28.48 MiB | 39.44 MiB |
| 两服务计费内存合计，不含容器基础系统 | 120.81 MiB | 105.76 MiB | 140.35 MiB |
| 两服务空闲 CPU 合计，占单核 | 0.361% | 0.446% | 0.383% |
| tailscale0 双向网卡字节 | 476 B/s | 495 B/s | 499 B/s |

控制节点 Headscale 服务计费内存为 15.45 MiB，空闲 CPU 为 0.096% 单核。
物理 eth0 还观察到约 2.7–3.0 KB/s，包含 LAN 广播、控制和其他后台流量，不能全部归因于应用。
underlay 和 tailscale0 是同一流量的不同层次，不应相加。没有做停用 VPN 的网卡背景对照实验。

## 实测发现与处理

1. Linux mDNS 初版绑定了本机单播 IP，只能发送发现包，无法接收组播响应。
   改为通配地址绑定，指定接口进行组播订阅和发送，三容器实测确认修复。
2. 仅按“100 个版本”分批不能限制长记录体积。最终版本同时按条数与字节数限制，
   并添加双向长记录回归测试。
3. Tailscale 不依赖 mDNS。最终实验从本机 Tailscale 节点列表探测服务，
   禁止物理应用端口作为退路，确认数据经过真实 WireGuard 隧道。
4. 测量脚本初版把第 28/30 个样本称为 P95，已经校正统计口径并重测。
   `lan-results.json` 明确保留为 rank28of30；最终结果采用 `lan-final.json` 的原始样本。

## 建议保留的产品规则

- 6 位临时码：60 秒有效、手动刷新；8 位固定码：持久保存、支持重置。
  两种码都只用于配对，已配对设备继续使用强随机凭据。
- 设备发现与数据授权分离。发现不会传递信任，也不会自动共享待办。
- 发现使用 LAN mDNS 与 Tailscale 单播两种提供者，合并到同一个候选列表。
  打开配对界面时应立即刷新；后台发现周期可以保持 30 秒。
- 普通修改采用约 120–250 ms 合并调度；空闲摘要核对 15–30 秒，离线退避。
- 同一套领域合并入口处理所有传输来源。正式应用需要单一写入协调器，
  不允许 Rust 网络线程与前端各自覆盖完整文档。
- WebDAV、局域网和 Tailscale 的交付状态分别记录，收到版本可继续中继，
  不改写原始作者与时间。此 demo 未接入 WebDAV，混合传输仍需单独集成验证。

## 尚未覆盖

三个客户端共享宿主机和时钟；虚拟网络实际为同宿主机 WireGuard 直连。
跨公网 NAT、DERP 中继、Wi-Fi 切换、纯 IPv6、移动端后台及数日运行尚未测试。
当前短码 PAKE 库未独立审计，实验密钥存在权限受限的 SQLite 中，
应用层 AEAD 还不是生产级 TLS/Noise 会话实现。正式接入前应处理系统密钥存储、
传输协议审计、前向保密、权限界面和安装包网络授权。

Node 常驻进程用于可复现演示。正式 Tauri 实现应复用已有 JS 环境并使用 Rust 网络层，
不能直接把 demo 的 RSS 当成正式应用新增内存。

原始证据：`build.json`、`lan-results.json`、`lan-final.json`、`tailscale-results.json`、
`soak-results.json`、`resource-results.json`。部署与操作命令见上一级 `README.md`。
