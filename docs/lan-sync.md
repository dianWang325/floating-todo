# 局域网与 Tailscale 同步

桌面应用可直接同步已配对设备的数据，无需部署同步服务器。功能默认关闭；WebDAV 可以独立使用，也可以与局域网同步同时开启。当前版本为实验性功能。

## 使用

1. 在两台设备的「设置 → 同步与备份 → 局域网与 Tailscale 同步」开启并应用设置。默认设备名称取自当前电脑（macOS ComputerName / Windows COMPUTERNAME）；保留自定义名称，旧默认“我的待办”按电脑名称处理。名称在应用设置时保存，不随系统改名实时更新，可在关闭同步时修改。
2. 允许系统的本地网络访问与入站 TCP 47831。真实局域网发现还需要 UDP 5353 多播；若网络隔离多播，可以输入 `http://设备IPv4:47831` 查找。
3. 在设备列表选择对方，输入对方的 6 位临时码或 8 位固定码，点击「配对并同步」。临时码每 60 秒切换，可手动刷新；固定码保存在本机，重启不变，支持重置。
4. 配对即授权合并双方全部待办、项目、标签、打卡记录、排序与备忘录。外观、本机提醒、同步地址和密码不随数据同步。
5. 同一事项并发修改时，默认显示版本模型判定的最新状态，其余分支仍保留。在「处理同步冲突」中可选择另一状态、编辑或另存任务。

Tailscale／Headscale 使用本机 Tailscale CLI 的 `status --json` 节点列表，不依赖虚拟网络转发多播。需要客户端已经登录、CLI 可执行，且网络 ACL 允许设备间 TCP 47831。找不到 CLI 时仍可手动输入 Tailscale IPv4。当前传输使用 IPv4，支持私有地址、链路本地地址和 Tailscale 的 100.64.0.0/10 地址，不支持公网地址、域名或 IPv6。

关闭同步会停止监听与发现，保留已配对凭据，重新开启可继续使用。撤销配对停止与该设备的直接通信，不删除已经同步到各设备的数据；若其他设备仍与其配对，仍可能通过其他设备中继。重置短码只影响新的配对，不撤销已有设备。配对中网络断开或本地凭据保存失败时可能仅一端完成确认，恢复后重新配对即可。

## 数据与保存顺序

- 继续使用 v3 文档及不可变 revision DAG，不新增第二套任务编号。每次修改生成版本 ID，不同实体自动合并，同一实体分支由既有确定性规则选取当前状态。
- 文档新增本机字段 `lan: { enabled, name }`，不进入同步版本或导出备份。设备 UUID 仍使用原有 `deviceId`。
- 前端仍为领域数据的单一写入者。`storage_save` 成功提交 SQLite 后，原生模块才更新可供其他设备读取的内存索引；保存失败的内容不会由原生模块发布。
- 两端各自拉取。先比较摘要，再分页查询 ID/hash 清单、获取缺失版本；校验内容摘要、格式、大小和时间后，经原有 SQLite generation 检查保存。重复批次幂等处理，同 ID 不同内容报错。
- 接收期间的本地修改会参与合并；正在编辑时延后应用。局域网与 WebDAV 网络合并串行执行。收到的局域网版本进入 WebDAV 待上传队列，WebDAV 保存成功的版本也会发布到局域网。
- 新增 `lan-vault.sqlite3` 存储加密的固定短码、已配对设备 ID/地址/密钥和配对尝试记录。AES-GCM 包装密钥由 macOS 钥匙串或 Windows 凭据管理器保管，凭据不写入普通备份或日志。

## 认证与资源限制

发现结果仅提供设备 ID、名称和协议，不授予读取权限。短码使用 SPAKE2 协商密钥，双方确认绑定设备身份、握手消息、短码类型和会话。读取请求与响应使用 AES-256-GCM，方向和用途经 HKDF 区分，响应绑定随机请求 ID。对外只提供读取版本接口，不允许网络请求直接写入本地文档。地址变更后，已配对设备须通过原有密钥认证才更新保存的地址。

每台设备最多 16 个配对。每分钟最多接受 5 次配对开始请求，计数持久化，待确认握手 30 秒失效。网络接口最多 8 个并发处理中请求，单请求处理超时 5 秒；客户端请求超时 4 秒，每台设备一轮同步最多 20 秒。消息体最多 512 KiB，单版本最多 128 KiB，每次读取最多 100 条且正文累计不超过 200 KiB。超限版本需要缩小内容；它们不会被静默丢弃。超前超过 5 分钟的修改会报错，需要校正设备时钟。

桌面保存新版本后合并 250 ms，主动向所有需要更新的已配对邻居发送加密摘要通知，排除已提供本批变化的来源；发送并发最多 4 个，但不截断邻居列表。接收端优先拉取通知来源，每轮最多两台设备。另每 60～75 秒随机触发一次全部邻居检查，分批排空待检查集合；离线节点仍遵循退避。摘要一致时不传输版本、不重写本地数据库。积压批次按 250 ms 调度继续处理。失败设备指数退避，最长 60 秒。发现列表最多保留 64 个候选，已知地址及 Tailscale 节点约每 30 秒检查，探测并发最多 4 个，每轮最多 32 个在线 Tailscale 节点并轮转覆盖其余节点。

本协议尚未经过独立安全审计，不提供每次会话的前向保密。读取请求重放不会写入数据；长期配对密钥泄露仍需撤销配对并重新建立。设备名称和发现元数据是公开的。端到端加密范围为局域网传输，WebDAV 远端文件仍遵循其原有安全模型。

## 验证与复现

原生库位于 `crates/lan-sync`，桌面集成位于 `src-tauri/src/lan.rs` 和 `src/sync-store.js`。

```sh
npm test
PLAYWRIGHT_CHANNEL=chrome npm run test:ui
cargo test --manifest-path crates/lan-sync/Cargo.toml --locked
cargo test --manifest-path src-tauri/Cargo.toml --lib --locked
npm run build -- --bundles app
```

原生单元测试覆盖双短码、错误短码限速及重启、密文篡改与身份绑定、凭据保存失败、短码刷新、分页中继、超大版本、同 ID 内容篡改及撤销。前端测试覆盖同步期间本地修改、编辑延迟、非法批次原子拒绝、保存失败重试和 WebDAV 中继；界面测试使用模拟原生命令验证配置、配对及撤销。

多播测试需要操作系统允许测试可执行文件的网络权限，因此默认跳过，在允许的网络测试机上显式运行：

```sh
cargo test --manifest-path crates/lan-sync/Cargo.toml --locked -- --ignored
cargo build --manifest-path crates/lan-sync/Cargo.toml --example bridge --locked
node tests/native-lan.mjs crates/lan-sync/target/debug/examples/bridge
```

`bridge` 仅是使用同一原生库的标准输入测试控制器，凭据在内存中，不是生产服务。测试脚本使用正式 JS 版本模型验证三节点发现、两种短码、三方冲突及替换、积压分页和撤销，生成 `test-results/native-lan.json`。LXC 复现可设置 `LAN_TEST_SSH=root@宿主机`，在 971–973 上预置同一二进制并传入其绝对路径；可选 `LAN_TEST_OVERLAY=IP1,IP2,IP3` 验证 CLI 自动发现并强制改用虚拟网络地址；`LAN_TEST_ENDPOINTS=IP1,IP2,IP3` 可指定真实局域网地址。

早期 Node demo 与本次原生传输协议不同，不互相配对；早期测试报告不能替代原生实现的结果。跨公网长期运行、Windows 实机防火墙交互和独立安全审计仍需后续验证。

- JS 数据测试 46 项、浏览器界面测试 37 项、Tauri 本地存储测试 4 项通过；界面测试的原生命令为模拟实现。

- 三个 LXC（每个 256 MiB、0.5 CPU）分别在以太网测试桥和现有 Headscale 网络验证自动发现、临时码/固定码配对、三方并发冲突保留与替换、230 个积压版本分页补齐和撤销配对，全部通过。原始结果：[局域网](validation/native-lan.json)、[Headscale](validation/native-headscale.json)。

## 多设备连接与传播

配对建立双向信任，双方保存彼此的设备 UUID、地址与配对密钥；只与明确配对的邻居交换版本，不会因为发现设备或收到第三方版本就自动增加配对。每个设备监听 TCP 47831，通过 HTTP 请求承载应用层加密消息，连接可复用，没有额外的 WebSocket 推送通道或中心主节点。发现只负责候选设备与已配对设备的认证地址更新。

- 原生模块在 SQLite 提交、发布索引后发送通知，连续修改合并 250 ms；收到通知时，前端合并调度一次拉取。配对双方会安排初始检查，启动、应用配置及“立即同步”也触发拉取。
- 通知只携带摘要，使用已有配对密钥认证和加密；不携带任务内容、不直接写库。每个邻居的待发送通知只保留一个，接收端相同来源和摘要重复通知被合并。不同来源也按设备 UUID 去重。
- 同步过程中收到新通知会保留待检查标记，完成后再检查；WebDAV 忙碌或正在编辑时，每秒本地检查一次是否可以恢复，不进行忙碌重入。两台并行邻居全部完成或超时后才提交收到的批次。
- 低频兜底每 60～75 秒标记全部邻居待检查，仍分批并行处理两台，每台最多 100 个版本，批次间按 250 ms 调度。恢复联网或窗口获得焦点时也启动全邻居检查；发现已配对设备的地址变化或故障恢复并通过认证后立即安排检查。

| 配对关系 | 数据传播 | 影响 |
| --- | --- | --- |
| 链形 A—B—C | B 保存 A 的版本后，C 从 B 拉取；A、C 无需直接配对 | 每跳增加等待；B 离线时暂时断开 |
| 环形 A—B—C—A | 可从多个方向得到同一版本 | 按原始版本 ID 去重，不产生新的版本或无限转发 |
| 中心辐射 S—A、S—B、S—C | S 汇总叶节点，再由其他叶节点读取 | S 的轮转速度与可用性成为瓶颈 |
| 多个环共享节点或密集互联 | 多条路径可中继相同版本 | 冗余提高可达性，也增加摘要与清单请求 |

抑制传播的关键是：收到版本不会重写版本 ID/时间或创造新编辑；相同 ID 与内容幂等合并，ID 相同但内容不同则报错；摘要一致立即停止，摘要不同也只获取本机缺少的版本。并发从两个邻居读取时可能重复下载同一版本，但保存时只保留一份，收敛后只剩周期摘要查询。LAN/WebDAV 中继同样保留原始版本身份。

当前没有生成树、选主或 TTL 转发机制；兜底轮询有随机抖动。它避免的是版本循环放大，不保证任意规模网络都没有拥塞：同时启动的设备可能集中请求中心节点，超过 8 个处理中请求会被拒绝并触发客户端退避；不收敛或被前端拒绝的版本也可能被再次读取。全量历史不一致时清单扫描仍有成本，单机轮转/批次上限用于约束资源。使用时应按必要关系配对；撤销一条边不会撤回已传播的数据，也不阻止其他仍配对的节点继续中继。

### 主动通知的边界与回退

通知会遍历全部已配对邻居，已提供所有新增版本的来源不会收到回传。如果同一保存批次混合了本地新修改和多个来源的版本，只要某邻居没有提供其中某项变化，就仍应通知它，避免因粗略排除整个来源列表而漏同步。来源记忆按版本内容摘要校验，只用于优化通知；最多记忆 4096 条尚未保存的版本，超限清空记忆可能产生额外通知，不影响版本正确性。

通知发送失败不持续重试或积累历史队列，依靠低频完整检查补齐；旧版节点不理解通知操作时，也仍可使用原有拉取协议。短时网络分区和应用休眠可能延迟传播，不保证固定时限。接收通知不会自动连接未配对设备；撤销配对同时清理对应待通知和待检查状态。

新增回归覆盖：超过两台邻居的通知全覆盖、批次合并、排除来源、重复摘要抑制、通知丢失后的轮询补齐、三节点环路收敛，以及同步过程中收到新通知后的第二次检查。上述历史 LXC 性能数值属于改造前版本，不作为本次通知机制的性能测量。
